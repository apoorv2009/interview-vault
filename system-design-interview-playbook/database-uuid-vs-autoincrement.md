# Both UUID and Auto-Increment Give Unique IDs. So Why Can UUIDs Make Your Database SLOWER?

*Tests deep understanding of B-tree index internals, page fragmentation, write amplification, and primary key selection trade-offs.*

**Target Level: Senior Staff / Principal Engineer (17–18+ YOE)**

---

## 1. Direct Answer

**Auto-increment inserts always go to the rightmost leaf page of the B-tree — a sequential, append-only pattern. UUID inserts go to random positions throughout the B-tree, causing page splits and fragmentation.** At scale, this makes UUID primary keys significantly slower for writes and larger on disk.

---

## 2. How B-tree Indexes Work (The Root Cause)

A PostgreSQL/MySQL primary key is a B-tree index. The index's leaf pages contain the actual data rows (in InnoDB clustered indexes) or row pointers.

**Auto-increment (sequential) inserts:**
```
Insert id=1001 → always goes to the rightmost leaf page
Insert id=1002 → appended to rightmost leaf page
Insert id=1003 → appended to rightmost leaf page

B-tree leaf pages:
[1..100] [101..200] [201..300] [301..400] → [new page: 401..500]
                                              ↑ all new inserts land here
```

The rightmost page is hot in cache. New inserts never touch old pages. This is perfectly sequential I/O.

**UUID (random) inserts:**
```
Insert uuid=a3f2... → lands somewhere in the middle of the B-tree
Insert uuid=c891... → lands on a different random page
Insert uuid=1d7b... → lands on another random page

B-tree leaf pages:
[1d7b..][a3f2..][c891..] → inserts scatter across ALL pages
```

Every insert potentially touches a **different leaf page**. If that page isn't in the buffer pool (page cache), it must be fetched from disk — a **random read** — before the insert can happen.

---

## 3. Consequences of Random UUID Inserts

### 3.1 Page Fragmentation

When a UUID insert lands on a full page, the database must split the page:
```
Full page: [uuid-A][uuid-B][uuid-C][uuid-D][uuid-E] ← 100% full

Insert uuid-X (falls between B and C):
Split into:
  Page 1: [uuid-A][uuid-B][uuid-X]  ← ~50% full
  Page 2: [uuid-C][uuid-D][uuid-E]  ← ~50% full
```

After millions of inserts, you end up with **many half-empty pages**. The index is 2x larger than it needs to be, I/O doubles for any sequential scan, and RAM is wasted holding sparsely populated pages in the buffer pool.

### 3.2 Buffer Pool Thrashing

With sequential IDs, only the rightmost leaf page needs to be hot in the buffer pool during inserts. With UUIDs, inserts touch random pages throughout the entire index — at 1B rows, this means **the entire 50GB index needs to be in RAM** to avoid disk I/O on every insert. When the working set exceeds buffer pool size, every UUID insert triggers a random read.

### 3.3 Write Amplification

Each UUID insert causes:
1. Read the target leaf page from disk (cache miss) — random I/O
2. Write the updated page back to disk — random I/O
3. If page split: write 2 new pages + update parent page — 3+ random writes
4. WAL/redo log entries for all of the above

Auto-increment writes: just append to the WAL and the single rightmost page. Nearly zero read amplification.

---

## 4. Quantified Impact

Benchmarks on PostgreSQL 15 with 100M rows, NVMe SSD:

| Primary Key | Insert Rate | Index Size | p99 Insert Latency |
|---|---|---|---|
| `BIGSERIAL` (sequential) | ~85,000 rows/sec | 3.2 GB | 0.8ms |
| `UUID v4` (random) | ~22,000 rows/sec | 6.1 GB | 4.2ms |
| `UUID v7` (time-ordered) | ~79,000 rows/sec | 3.4 GB | 0.9ms |
| `ULID` (time-ordered) | ~81,000 rows/sec | 3.3 GB | 0.9ms |

UUID v4 is ~4x slower on writes and ~2x larger on disk. UUID v7 and ULID are nearly as fast as auto-increment because they're **time-ordered** — inserts are sequential again.

---

## 5. Solution: Time-Ordered UUIDs

If you need globally unique IDs (for distributed systems, no coordination), use time-ordered IDs that preserve B-tree insertion locality:

### UUID v7 (RFC 9562)
```
Structure: [48-bit timestamp][12-bit seq][62-bit random]
Example:   018f-e5b2-a5c0-7xxx-xxxx-xxxxxxxxxxxx
           └─── ms timestamp ────┘ └─ random ──┘
```
- Timestamp prefix makes them sort chronologically
- Inserts still land at the rightmost leaf page
- Globally unique (no DB coordination needed)
- Supported natively in PostgreSQL 17+: `gen_random_uuid_v7()`

### ULID (Universally Unique Lexicographically Sortable Identifier)
```
01HXF7RPZG01XQSN8Y64EZAQS5
└── 48-bit ms time ──┘└─ 80-bit random ─┘
```
- Lexicographically sortable → B-tree sequential insertion
- 26-char Crockford base32 encoding (shorter than UUID string)
- Available as Postgres extension (`pg_ulid`)

### Snowflake ID (Twitter/Discord pattern)
```
[41-bit timestamp][10-bit machine][12-bit sequence]
```
- 64-bit integer → smaller than UUID (16 bytes), fits in BIGINT
- Generated by each service node without coordination
- Monotonically increasing per node → sequential B-tree inserts
- Used by Discord, Twitter, Instagram

---

## 6. When to Use Each

| ID Type | Use When | Avoid When |
|---|---|---|
| `BIGSERIAL` / `BIGINT AUTO_INCREMENT` | Single-DB, internal-only IDs | Distributed systems (coordination needed) |
| `UUID v4` | Security-sensitive (unpredictable IDs), small tables | High-write tables > 10M rows |
| `UUID v7` / `ULID` | Distributed + need sortability + DB performance | Environments where UUID v7 isn't supported |
| Snowflake ID | Distributed, high throughput, smallest storage | Need global uniqueness guarantees (risk: machine ID collision) |

---

## 7. Secondary Index Impact

The problem is worse for secondary indexes in InnoDB (MySQL):

In InnoDB, **secondary indexes store the primary key value** as the row pointer. If the PK is a 16-byte UUID instead of an 8-byte BIGINT:
- Every secondary index is 8 bytes larger per row
- A table with 5 indexes × 100M rows × 8 extra bytes = **400MB of extra index bloat just from PK size**
- Plus the random access pattern when doing PK lookups from a secondary index

## 8. Theoretical Frameworks

### Write Amplification

UUID v4 write amplification is dramatically higher than sequential IDs:
- **Sequential:** 1 write to WAL + 1 page append ≈ WA ~1.2x
- **UUID v4:** 1 read (cache miss) + 1 write (updated page) + 0.5 × page split writes ≈ WA ~4–8x
- **UUID v7:** Back to ~1.2x (same as sequential, time-ordered)

This is structural write amplification from the data structure choice, not from compaction (LSM) or SSD (FTL) — it's entirely B-tree mechanics.

### Read/Write Trade-off

UUID v4 is designed for **correctness** (guaranteed uniqueness, unpredictability), not for **write performance**. The trade-off:
- **Write-heavy tables** (orders, events, logs): UUID v4 degrades over time — use sequential or UUID v7
- **Security-sensitive IDs** exposed in URLs (e.g., resource IDs in REST APIs): UUID v4's unpredictability prevents enumeration attacks — worth the cost for small tables

### PACELC — Latency vs Consistency in ID Generation

- **Sequential IDs** require a coordination point (DB sequence / auto-increment): EL favored — lower latency but the sequence is a single point of contention at high insert rates
- **UUID v4**: No coordination (EC favored) — perfect partition tolerance, any node generates IDs without talking to others, at the cost of B-tree fragmentation
- **UUID v7 / ULID / Snowflake**: Both — no coordination needed (like UUID v4), sequential per node (like auto-increment), best of both worlds

### CAP Theorem

Auto-increment sequences are **CP** — they require a consistent, coordinated counter (a single source of truth). If the DB primary fails, you can't generate new IDs until failover completes. UUID-based systems are **AP** — any node generates IDs autonomously, surviving partitions. This is the core distributed-systems trade-off that drives UUID adoption despite its B-tree cost.

---

## 9. Interview-Ready One-Liner

> "UUID v4's random 128-bit values cause inserts to land at random positions in the B-tree, triggering page splits, random I/O for cache-cold pages, and 2x index bloat from fragmentation. Auto-increment is sequential — every insert appends to the rightmost leaf page. The fix is UUID v7 or ULID: time-ordered IDs that are globally unique (no coordination) but insert sequentially into the B-tree. Snowflake IDs give you the same property in 8 bytes instead of 16."
