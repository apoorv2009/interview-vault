Part 1 — Introduction to System Design Interview
1What is a System Design Interview?›
  • Assesses ability to design large-scale software systems — for SWE, architect, DevOps roles.
  • Open-ended, unlike coding interviews — no single "correct" answer. It's about approach + reasoning, not producing code.
  • What it checks:
    • Problem-solving on ambiguous, open-ended problems
    • Technical knowledge — DBs, APIs, caching, load balancing, protocols
    • Scalability / reliability thinking
    • Trade-off reasoning — why this choice, not just what
    • Communication — it's a dialogue, whiteboard included
  • Not about: a "perfect" answer, or memorizing tool trivia.
Remember: they're grading how you think, not what you land on.
2Functional vs. Non-functional Requirements›

Functional — WHAT

  • Actions the system must perform
  • Auth validates credentials & access
  • Browse → cart → checkout
  • Forms the backbone of the design

Non-functional — HOW

  • Scalability, performance, availability, security
  • Quality attributes, not features
  • Shows depth / robustness
  • Interview approach: clarify → prioritize → discuss trade-offs (e.g. read-optimized often ⇒ slower writes) → use real examples → keep it balanced.
  • Interviewers often leave requirements vague on purpose — asking clarifying Qs is part of the test.
3Back-of-the-Envelope Estimations›
  • Quick napkin math to sanity-check feasibility, load, bottlenecks — not precision.
  • Techniques: rule of thumb, approximation (round numbers), breakdown & aggregate (split into parts, sum up), sanity check vs known systems.
  • Types: load, storage, bandwidth, latency, resource (servers/CPU) estimation.
  • Worked examples:
    • Load: 100M DAU × 10 posts = 1B/day → ÷86,400s ≈ 11,574 req/s
    • Storage: 500M users × 2 photos × 2MB = 2B MB/day
    • Bandwidth: 10M users × 4 Mbps = 40M Mbps
    • Latency (sequential) = sum of hops; (parallel) = max of hops
    • Resource: 10,000 req/s × 10ms = 100,000 ms/s → ÷1,000ms/core = 100 cores

4Things to Avoid During the Interview›
  • Don't skip clarifying requirements or oversimplify the problem.
  • Don't dive into low-level details before the high-level shape exists.
  • Don't get married to your first idea — stay flexible, use interviewer hints.
  • Don't skip trade-off discussion — every decision has one, justify it.
  • Don't ignore non-functional requirements or real constraints (cost, time, existing stack).
  • Don't under-communicate — it's a dialogue, not a monologue.
  • Don't fake confidence — saying "I don't know, but here's how I'd find out" beats guessing wrong.
Part 2 — Glossary of System Design Basics

Core building blocks: distributed systems traits → load balancing → caching → partitioning → indexes → proxies → replication → SQL/NoSQL → CAP/PACELC → consistent hashing → realtime protocols → Bloom filters.

5System Design Basics›
  • Three questions for any large system: what pieces exist? how do they interact? what are the right trade-offs?
  • Scaling before it's needed is usually bad business — but a little forethought saves pain later.
6Key Characteristics of Distributed Systems›
  • Scalability — grow without losing performance.
    • Horizontal (add more machines — Cassandra, MongoDB) vs Vertical (bigger machine — MySQL, usually = downtime + a ceiling)
  • Reliability — keeps working correctly through failures, via redundancy of software + data.
    • Fault tolerance ≠ reliability: FT = system-centric ("does it keep running when a part breaks"); Reliability = user-centric, measured via uptime / MTBF over time.
  • Availability — % of time it's operational. Reliable ⇒ available, but available ≠ reliable (can look fine for years, then fail hard — e.g. a system with no security testing that later suffers a breach).
  • Efficiency — measured by latency (time to first result) + throughput (results per second).
  • Manageability — how easily it's diagnosed, updated, operated; early fault detection cuts downtime.
7Load Balancing›
  • Sits between client and servers, spreads traffic, stops routing to unhealthy/slow servers.
  • Can live at 3 layers: user↔web, web↔app/cache, app↔database.
  • Benefits: faster/uninterrupted service, less downtime, easier ops, predictive bottleneck insight.
  • The LB itself is a SPOF → pair two LBs, each monitoring the other's health (active takes over on failure).
8Load Balancing Algorithms›
  • Round RobinCycles servers in fixed order. Simple, no load-awareness. Good: homogeneous, stateless.
  • Least ConnectionsSends to server with fewest active connections. Dynamic, load-aware. Good: heterogeneous / variable traffic.
  • Weighted Round RobinRound Robin + capacity weights. Good: mixed-capacity server pools.
  • Weighted Least ConnectionsLeast Connections + weights — most balanced, most complex.
  • IP HashHash client IP → same server every time. Gives session stickiness; uneven if IPs cluster.
  • Least Response TimeSends to the currently-fastest-responding server. Good: real-time, low-latency apps.
  • RandomPicks any server at random. Trivial, evens out over time, no session affinity.
  • Least BandwidthRoutes to server using least bandwidth right now. Good: video/CDN-heavy traffic.
  • Custom LoadYour own metrics (CPU, memory, I/O) drive the decision. Max flexibility, max complexity.
9Caching›
  • Fast storage layer between app and the real data source — exploits locality of reference (recently used data gets reused).
  • Types: in-memory (Redis/Memcached), disk, database, client-side, server-side, CDN, DNS.
  • Write strategies:
    • Write-through — write cache + DB together → consistent, safe, but slower writes
    • Write-around — write DB only, skip cache → fresh writes cause a cache miss on read
    • Write-back — write cache only, flush to DB later → fast, but risk of loss on crash
  • Invalidation methods: purge, refresh, ban (pattern-based), TTL expiry, stale-while-revalidate (serve stale instantly, refresh in background).
  • Read strategies: read-through (cache manages the fetch-on-miss itself) vs cache-aside/lazy-loading (app manages it — safer if cache dies, app can fall back to DB).
  • Eviction policies: FIFO, LIFO, LRU, MRU, LFU, Random.
10Data Partitioning›
  • Split a big DB into independent shards, each on its own node — better perf + scalability.
  • Horizontal (by rows / sharding, e.g. by region) — risk: uneven shards if the key isn't chosen well.
  • Vertical (by columns, e.g. profile vs orders) — reduces scanned data per query.
  • Hybrid — both combined.
  • Criteria: hash-based (fixes server count — consistent hashing fixes that), list-based, round-robin, composite.
  • Pain points: cross-shard joins (⇒ denormalize, accept some inconsistency risk), no cross-server foreign keys (⇒ enforce in app code), rebalancing is hard without downtime.
11Indexes›
  • A data structure — like a book's table of contents — that stores a column's values + pointers to full rows, so lookups skip a full scan.
  • Critical when data is huge but each record is tiny (can't brute-force scan terabytes for a 1KB record).
  • Trade-off: every insert/update/delete must also update the index → slower writes. Only index what you actually query on; drop unused indexes; skip them entirely if the table is write-heavy and rarely read.
12Proxies›

Forward Proxy

  • Sits in front of clients
  • Hides the client's identity from the server
  • Used for caching, filtering, logging, request rewriting
  • Can merge duplicate concurrent requests ("collapsed forwarding")

Reverse Proxy

  • Sits in front of servers
  • Hides the server's identity from the client
  • Used for caching, load balancing, routing
Rule of thumb: protect clients → forward proxy. Protect servers → reverse proxy.
13Redundancy and Replication›
  • Redundancy = duplicate critical parts/data so no single failure takes the system down.
  • Replication is usually primary → replica(s); primary takes all writes, replicas confirm receipt.
  • Synchronous — primary waits for replica confirmation before ack'ing the write. Strong consistency, higher latency.
  • Asynchronous — primary acks immediately, replicas catch up later. Fast, but a window of staleness.
  • Semi-synchronous — at least one replica must confirm; others lag async. Middle ground.
14SQL vs. NoSQL›

SQL

  • Fixed schema, tables + joins
  • ACID transactions — all-or-nothing
  • Great for complex queries / analytics
  • Scales vertically by default
  • Best: finance, orders, anything needing strict consistency

NoSQL

  • Flexible / schema-less records
  • Document, key-value, wide-column, graph
  • Usually BASE / eventual consistency
  • Scales horizontally, built-in sharding
  • Best: massive scale, evolving data, simple fast lookups
  • CAP lens: SQL usually leans CP; Dynamo-style NoSQL usually leans AP.
  • NewSQL (Spanner, CockroachDB) tries to blend both — SQL semantics, distributed backend.
  • Don't force a single choice — polyglot persistence is normal (e.g. SQL for payments, NoSQL/Redis for location pings & caches, graph DB for relationships).
15CAP Theorem›
  • A distributed system can't guarantee all three at once:
    • Consistency — every node sees the same data at the same time
    • Availability — every request to a healthy node gets a response
    • Partition tolerance — keeps working through a network split
  • Real rule: partitions are inevitable, so "CA" isn't really an option — in a partition, pick C or A.
  • Why: to stay consistent you'd have to stop serving the out-of-date side of the split — which breaks availability.
16PACELC Theorem›
  • CAP is silent on the no-partition case — PACELC fills that in.
  • If Partition → trade Availability vs Consistency (same as CAP).
  • Else (normal operation) → trade Latency vs Consistency.
  • Examples: Dynamo/Cassandra = PA/EL · BigTable/HBase = PC/EC · MongoDB default = PA/EC (writes to majority flips it to PC/EC).
17Consistent Hashing›
  • Problem with naive hash % N: adding/removing a server changes N → almost everything remaps → mass data movement.
  • Fix: arrange nodes on a hash ring; each node owns a range. A key's hash falls somewhere on the ring → that's its node. Adding/removing a node only disturbs its neighbor, not the whole cluster.
  • Virtual nodes (Vnodes): split the ring into many small sub-ranges per physical node instead of one big range each →
    • rebalancing spreads across many nodes, not just neighbors
    • easy to give stronger servers more sub-ranges
    • fewer hotspots
  • Replication: key's coordinator node stores it, then replicates clockwise to N-1 more nodes (N = replication factor), usually async.
  • Used by: Amazon Dynamo, Apache Cassandra.
18Long-Polling vs WebSockets vs SSE›
  • Ajax Polling — client asks every N ms, server replies even with nothing new. Simple, wasteful (empty responses).
  • Long-Polling ("hanging GET") — server holds the request open until it has data, then replies; client immediately re-polls. Less waste than plain polling, still needs periodic reconnects.
  • WebSockets — one persistent, full-duplex TCP connection after a handshake; either side can push data anytime. True real-time, two-way.
  • Server-Sent Events — one persistent connection, server → client only. Simpler than WebSockets when the client never needs to talk back.
19Bloom Filters›
  • Answers "have I seen this before?" using a tiny bit array + k hash functions — no items are ever actually stored.
  • Add: hash the item k times → set those k bit positions to 1.
  • Check: hash again → if any bit is 0 → definitely not present. If all bits are 1 → probably present (could be a false positive).
  • No false negatives ever (bits only ever flip 0→1, never reset) — false positives are the only error, and only in the "yes" direction.
  • Tuning: bigger bit array (m) ↓ false-positive rate; more items (n) ↑ it; hash count (k) has a sweet spot for a given m, n.
  • Can't delete, can't list contents, can't count — just add + check, both O(1) regardless of set size.
  • Used to guard expensive lookups (DBs, caches, browsers, network gear) — skip the real check when the filter says "no."
30-sec interview answer: "Bit array + a few hash functions. Adding sets bits, checking tests them. Missing bit = definitely absent, all bits set = probably present. No false negatives, occasional false positives, constant time, tiny memory — great in front of an expensive lookup."
