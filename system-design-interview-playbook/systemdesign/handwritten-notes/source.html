Part 1 — Introduction to System Design Interview (Q1–Q4)

1.What is a System Design Interview?

Ans: Assesses your ability to design large-scale software systems — open-ended, no single "correct" answer. It's about approach and reasoning, not producing code, and not memorizing tool trivia.

What it checks

  • Problem-solving on ambiguous problems
  • Technical knowledge — DBs, APIs, caching, LB, protocols
  • Scalability / reliability thinking
  • Trade-off reasoning — why, not just what
  • Communication — it's a dialogue

2.Functional vs. Non-functional Requirements?

Ans: Functional = what the system does (auth, browse → cart → checkout). Non-functional = how it performs — scalability, performance, availability, security. Clarify both, prioritize, then discuss trade-offs (e.g. read-optimized often ⇒ slower writes).

AspectFunctionalNon-functional
DefinesActions performedQuality of performance
ExamplesAuth, checkoutScale, uptime, security
RoleBackbone of designShows depth & robustness

3.What are Back-of-the-Envelope Estimations?

Ans: Quick napkin math to sanity-check feasibility, load, and bottlenecks — not precision. Techniques: rule of thumb, approximation (round numbers), breakdown & aggregate, sanity check vs known systems.

  • Load: 100M DAU × 10 posts = 1B/day → ≈ 11,574 req/s
  • Resource: 10,000 req/s × 10ms = 100 cores needed

Latency numbers worth knowing

4.What Should You Avoid in the Interview?

Ans: Don't skip clarifying requirements, don't dive into low-level details too soon, don't get married to your first idea, and don't skip trade-off discussion. It's a dialogue — under-communicating or faking confidence both read badly.

7 things to avoid

  • Skipping clarification
  • Details before the big picture
  • Rigid on your first idea
  • Ignoring trade-offs
  • Ignoring non-functional reqs
  • Under-communicating
  • Overconfidence
Part 2 — Glossary of System Design Basics (Q5–Q19)

5.What's the Basic Approach to System Design?

Ans: For any large system, ask: what architectural pieces exist, how do they interact, and what are the right trade-offs? Scaling before it's needed is usually bad business — but a little forethought saves pain later.

3 questions to ask

  1. What pieces can be used?
  2. How do they work together?
  3. What's the right trade-off?

6.Key Characteristics of Distributed Systems?

Ans: Scalability (horizontal vs vertical), reliability (keeps working through failures, via redundancy), availability (% uptime — reliable ⇒ available, not the reverse), efficiency (latency + throughput), and manageability (how easily it's diagnosed and fixed).

Cassandra/MongoDB → horizontal · MySQL (classic) → vertical

7.What is Load Balancing?

Ans: Sits between client and servers, spreading traffic and skipping unhealthy/slow servers. Can live at 3 layers: user↔web, web↔app/cache, app↔database. The LB itself is a SPOF, so pair two — each monitoring the other's health.

Three places to slot in a load balancer

8.What are the Load Balancing Algorithms?

Ans: Round Robin and Random are the simplest (no load-awareness). Least Connections / Weighted variants react to real load. IP Hash gives session stickiness. Least Response Time and Least Bandwidth react to live performance. Custom Load lets you define your own metrics.

AlgorithmBest for

Least ConnectionsVariable traffic

Weighted Least Conn.Most balanced, complex
IP HashSession stickiness
Least Response TimeReal-time, low latency
RandomSimple deployments
Least BandwidthVideo / CDN traffic

9.What is Caching, and How Do You Invalidate It?

Ans: A fast storage layer between app and source, exploiting locality of reference. Write-through/around/back trade consistency for write speed. Invalidate via purge, TTL expiry, or stale-while-revalidate. Evict via LRU, LFU, FIFO, or random.

Cache-aside: hit → return · miss → fetch, store, return

10.What is Data Partitioning?

Ans: Splitting a big DB into shards, each on its own node. Horizontal = by rows (risk: uneven shards). Vertical = by columns. Cross-shard joins and rebalancing are the pain points — hash-based partitioning fixes the server count unless you use consistent hashing.

Same table, two ways to cut it

11.What are Indexes, and Why Do They Slow Writes?

Ans: A data structure — like a book's table of contents — storing a column's values + pointers to full rows, so lookups skip a full scan. Trade-off: every write must also update the index. Only index what you actually query on.

The trade-off

OperationWith index
ReadsMuch faster ✓
WritesSlower — index updates too

12.Forward Proxy vs Reverse Proxy?

Ans: A forward proxy sits in front of clients and hides the client's identity from the server. A reverse proxy sits in front of servers and hides the server's identity from the client. Rule of thumb: protect clients → forward; protect servers → reverse.

Same shape, opposite job

13.Redundancy vs Replication?

Ans: Redundancy = duplicate critical parts/data so no single failure takes the system down. Replication is usually primary → replica(s). Synchronous = strong consistency, higher latency. Asynchronous = fast, but a staleness window. Semi-sync is the middle ground.

Sync trades latency for certainty

14.SQL vs. NoSQL — How Do You Choose?

Ans: SQL = fixed schema, ACID, scales vertically, great for complex queries. NoSQL = flexible schema, usually BASE/eventual consistency, scales horizontally. CAP lens: SQL leans CP, Dynamo-style NoSQL leans AP. Most real systems mix both — polyglot persistence.

AspectSQLNoSQL
SchemaFixed, joinsFlexible
ConsistencyACIDUsually BASE
ScalingVerticalHorizontal
Best forFinance, ordersMassive scale

15.What is the CAP Theorem?

Ans: A distributed system can't guarantee Consistency, Availability, and Partition tolerance all at once. Since partitions are inevitable, "CA" isn't really an option — in a partition, pick C or A.

CP and AP are the real choices

16.What is the PACELC Theorem?

Ans: CAP is silent on the no-partition case — PACELC fills it in. If Partition → trade Availability vs Consistency. Else → trade Latency vs Consistency. Dynamo/Cassandra = PA/EL · BigTable/HBase = PC/EC · MongoDB default = PA/EC.

PAC = CAP · ELC = the normal-operation case

17.What is Consistent Hashing?

Ans: Naive hash % N breaks almost every mapping when N changes. Fix: arrange nodes on a hash ring — a key's hash lands on the ring and belongs to the next node clockwise, so adding/removing a node only disturbs its neighbor. Vnodes split each node into many small sub-ranges for even load.

Used by Amazon Dynamo, Apache Cassandra

18.Long-Polling vs WebSockets vs SSE?

Ans: Long-polling holds the request open until data exists, then the client re-polls. WebSockets keep one persistent, full-duplex connection — either side can push anytime. SSE is persistent but one-way, server → client only.

↑ client→server · ↓ server→client

19.What are Bloom Filters?

Ans: Answers "have I seen this?" with a tiny bit array + k hash functions — no items are stored. Any 0 bit → definitely not present. All bits 1 → probably present (maybe a false positive). No false negatives ever, and both add/check are O(1).
