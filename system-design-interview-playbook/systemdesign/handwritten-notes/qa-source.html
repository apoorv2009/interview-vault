Auth & Caching (3 questions)

1.JWT exists but API returns 401 — why, and how do you debug it?

Ans: A valid JWT must pass 4 gates in order — format, signature, time/issuer claims, permissions. Fail any one = 401. Usual suspects: expired token, wrong signing secret, audience mismatch, or clock skew between client and server.

  • Debug: decode (no verify) → check exp/iss/aud
  • Debug: test with raw curl, skip the app
  • Debug: read the server's exact error string

The 4 gates — fail any one → 401

2.An OTP is valid for 30s and never stored server-side — how does the server verify it?

Ans: Phone and server both run the same HMAC algorithm on the same shared secret + the current 30-second time step — independently landing on the same 6-digit code. Nothing is stored or transmitted ahead of time; it's computed fresh, twice, in parallel.

HMAC(secret, time-step) — computed twice, matched once

3.Design a cache that never slows down no matter how many items you store.

Ans: HashMap + Doubly Linked List. HashMap gives O(1) lookup; the list's head/tail give O(1) "most-recent" / "least-recent" tracking. The HashMap stores key → pointer to the node, so both structures stay in sync in O(1) — regardless of cache size.

O(1) every step

GET(key)map lookup + move to head
PUT when fullevict tail + map delete
PUT newadd head + map insert
Concurrency (2 questions)

4.Two threads update the same data simultaneously — how do you prevent a race condition?

Ans: The outcome depends on timing — both threads read a stale value, both compute from it, whichever writes last silently overwrites the other ("lost update"). Fix: serialize the read-modify-write, one of three ways.

3 ways to serialize

ApproachHowBest for
Pessimistic lockBlock others until doneHigh contention
OptimisticVersion column, retry on conflictLow contention
Atomic instr.Hardware compare-and-swapSimple counters

5.Two users hit the same API at the same millisecond, both pass validation, both insert — now you have duplicates. Fix?

Ans: Validation runs before the insert, so "check, then act" leaves a gap — both requests see "doesn't exist," both proceed. Stop trusting the app-level check; make the database itself reject the second write.

3 ways to close the gap

  • Unique constraint — DB rejects the 2nd insert outright
  • Idempotency key — dedupe by request ID
  • Distributed lock — serialize the whole window
DRM, Data Structures & TTL (3 questions)

6.You try to screen-record Netflix but only get a black screen. Why?

Ans: Netflix never even "sees" the recording attempt — the OS itself refuses to capture that window, because Netflix flagged its video surface as protected content (HDCP). The compositor blacks it out before any recording tool gets a frame.

Who blocks what

LayerRole
App (Netflix)Marks its surface HDCP-protected
OS compositorExcludes that surface from the capture buffer
Screen recorderGets a black frame — never sees content

7.How is Gmail's username-availability check instant?

Ans: Gmail uses a Bloom Filter — a tiny bit array in RAM answering "taken?" in <1ms with no false negatives, only occasional false positives. No usernames are actually stored in it.

8.Instagram Stories expire after exactly 24 hours. What mechanism tracks and enforces that?

Ans: No per-story timer runs anywhere. Every story stores an expires_at timestamp once, at creation. The server just filters it out of any query once that time has passed.

No timers, just a filter

  • expires_at = created_at + 24h — stored once
  • Every fetch: WHERE expires_at > now()
  • Background sweep / TTL index only for storage reclaim, not enforcement
E-Commerce & Git Workflow (2 questions)

9.Products show 'In Stock' but are unavailable at checkout. How do you debug and fix this?

Ans: A classic eventual consistency bug — the listing page reads stale state (cache/replica/CQRS lag) while checkout enforces real-time truth. Also check for a non-atomic read-modify-write at checkout itself — that alone oversells even with fresh reads.

Root causes, by likelihood

CauseLikelihood
Stale cache / CDN TTLHigh
Race at checkout (no lock)High
Read replica lagMedium
CQRS read-model delayMedium
WMS batch-sync delayMedium

10.Your branch is 200 commits behind main. Merge or rebase?

Ans: Depends on one question — is the branch shared with others, or yours alone? Never rebase a shared branch.

Branch is...Use
Yours aloneRebase — clean linear history
Shared with othersMerge — never rewrite shared history
Incident Response & Security (3 questions)

11.CTO calls at 3 AM — your S3 bucket got encrypted, ransom note in metadata. First 15 minutes?

Ans: Do NOT start recovering data yet — the attacker may still have access, and restoring now just means they re-encrypt it again. First: stop the bleeding, lock them out, preserve evidence. Recovery comes after.

First 15 minutes

  1. Revoke / rotate the compromised credentials
  2. Block bucket writes (deny-all policy)
  3. Preserve evidence — CloudTrail logs, snapshot
  4. Then, only then: begin recovery

12.SSL cert expired Sunday morning, site is down. Next 10 minutes?

Ans: Don't panic — verify the problem, tell your team, then fix it. Jumping straight to a fix without understanding the scope can make things worse.

Next 10 minutes

  1. Confirm it's really the cert (not DNS/other)
  2. Notify team / status page
  3. Reissue + deploy new cert
  4. Postmortem: automate renewal (ACME/cert-manager)

13.What measures protect APIs from unauthorized access in a microservices architecture?

Ans: Don't open with "use OAuth2" — start from a threat model. In microservices, East-West traffic (service-to-service) is the blind spot — often implicitly trusted. Defense in depth beats any single control.

TrafficRiskDefense
North-SouthClassic boundaryOAuth2/JWT at gateway
East-WestOften trusted by defaultmTLS + per-service JWT
Compromised serviceLateral movementLeast-privilege scopes
Microservices & Architecture (3 questions)

14.A user places an insurance order — can I call multiple downstream services directly now?

Ans: No — not from the originating service. Calling Underwriting, Payment, and Notification synchronously from one request thread creates a distributed monolith disguised as microservices.

Why direct fan-out bites

  • Cascading failure — one slow service blocks the whole caller thread pool
  • No atomicity — partial failure, no rollback across calls
  • Tight coupling — every downstream change forces a redeploy

Fix: async fan-out via events/saga — not sync calls from the origin

15.What microservice architecture do companies actually use in real projects?

Ans: Textbooks show clean boxes with arrows; production is messier — a hybrid of decomposed services, shared libraries, and platform teams. gRPC internally, REST only at the boundary.

Textbook fictionProduction reality
Every service independently deployableShared DB schemas, monorepo coupling
Clean REST everywheregRPC internally; REST only at the edge
Service mesh from day oneRolled out incrementally; many bypass it

Payments & Pricing (2 questions)

17.A passenger swipes a card offline, bank unreachable. Approve without a balance check, and prevent fraud?

Ans: You can't verify the balance, so don't try — approve against a pre-computed risk budget stored locally, sign the transaction cryptographically, and reconcile against the real ledger the moment connectivity returns. Same idea as EMV chip offline counters.

Approve → cap risk → reconcile

  • Terminal enforces an offline floor limit + cumulative exposure cap per card
  • Signed transaction record — non-repudiable proof it happened
  • Real balance/fraud check happens at reconnect — issuer/airline eats loss beyond the floor limit

18.A user thinks airline prices rise because they searched again. What actually changed?

Ans: The price didn't change because they searched — that's correlation mistaken for causation. Prices are recomputed fresh on every request by a pricing engine reacting to inventory, time, and demand that move independently of any one searcher.

What actually moves the price

  • Cache TTL expiry — recomputed periodically anyway
  • Seat-class inventory shifts
  • Real competitor / demand-based repricing
  • (Rarely, legitimately) personalization — not "tracking your search"
RAG (3 questions)

19.5000 PDFs — text, tables, charts, scanned images. Build a RAG chatbot that answers accurately.

Ans: "Chunk and embed" fails immediately — scanned pages have no text layer, naive splitting destroys tables, charts are invisible to text parsers. You need a pipeline that routes each content type separately.

  1. Classify: text layer vs scanned page
  2. OCR scanned pages (Tesseract / Textract)
  3. Extract tables as atomic chunks — never split
  4. Describe charts via a vision model
  5. Smart / hierarchical chunking by section
  6. Embed + store in vector DB
  7. Hybrid retrieval: semantic + BM25 keyword

20.RAG retrieves top-5, but the answer is in chunk #12. Raising top-K to 20 blows the context window. Fix?

Ans: One-stage retrieval is doing two conflicting jobs — cast a wide net to find #12, and be precise enough to rank it top-5. Split into two stages instead.

StageJobCost
Retrieve broadtop-50/100, wide netLow
Re-rankcross-encoder, narrow to top-5Higher, small set

Recall from stage 1, precision from stage 2

21.Your RAG data changes every hour. How do you version it without breaking the system?

Ans: Treat RAG like static data and you're one update from an outage. Three separate things need versioning, each with its own rule.

LayerRule
DocumentsVersioned source of truth per doc
EmbeddingsRe-embed on model change
IndexAtomic swap — never mutate in place
Reliability & Scaling (2 questions)

22.Your API is fine at 1,000 users but crashes at 100,000. What do you check first?

Ans: "Crashes at scale" is a symptom, not a diagnosis — eliminate layers systematically, starting with whatever doesn't scale linearly with users.

Check first, in order

  1. DB connection pool exhaustion — most common
  2. N+1 queries, invisible at low volume
  3. Single-threaded bottleneck
  4. Memory leak under sustained load

23.How do 3 billion Instagram users keep scrolling forever without melting the servers?

Ans: Instagram never fetches "the feed" — it fetches a small page at a time via a cursor that remembers exactly where you left off, paired with a ranking service that decides what's next, not just pagination that decides position.

  • Fetch 10–20 posts at a time, not 1,000
  • Cursor encodes exact position — offset breaks under concurrent inserts
  • Ranking service pre-computes (or computes just-in-time) ordering
Streaming, Vector DB & Video (3 questions)

24.How does Netflix switch subtitles instantly mid-movie without reloading?

Ans: Subtitles are not part of the video — they're tiny separate text files fetched independently. Switching language just swaps which file is being read; the video stream never stops.

25.Our vector database costs are increasing rapidly. How do you optimize and reduce them?

Ans: Vector DB cost is overwhelmingly a memory cost, not storage — indexes want to sit fully in RAM for low-latency search, and teams keep every vector "hot" at full float32 precision. Layered fix.

  • Quantize — shrink each vector (float32 → int8/binary)
  • Tier — move cold vectors to disk / object storage
  • Dedup — delete stale vectors, reduce dimensions

26.YouTube has the same video in 1080p and 144p. Does the server store separate files for each quality?

Ans: Yes — separate encoded versions per quality, pre-transcoded at upload time. But not as whole files: each quality is split into small ~2-second chunks (adaptive bitrate), and audio is stored once, shared across every video quality.

  • Every quality pre-transcoded once at upload, not on demand
  • Split into ~2s chunks — client switches quality between chunks
  • Audio stored once per language, shared across all video qualities
